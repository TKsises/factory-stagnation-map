## 2. アプリの中身

### 解こうとしている現象

工場のリードタイムのうち、実際に加工している時間はごく一部で、大半は「次の工程を待っている時間」＝**滞留**。
これを可視化し、凍っている運転資金の額に翻訳する。

### 機能一覧

**入口（2通り）**
- 工程実績CSVの読み込み（UTF-8 / Shift_JIS 自動判定、自前パーサ）
- Smart Craft API からの直接取得（中継サーバー経由）
- 検証用データを3種類内蔵（CSVが無くてもURLを開けば全機能を試せる）

**画面（タブ7つ）**

| タブ | 中身 |
| --- | --- |
| 滞留マップ | 工程を線で繋ぎ、線の上に「山」を立てる。山が高い＝長く止まっている。工程数が増えても横に伸びず折り返す。山も工程も押せる |
| ロット別実績 | 1件ずつ追える。各行に加工（濃い帯）と滞留（斜線の帯）の比率 |
| 原価と金額 | 品目別単価を手入力 → 凍結額・1日あたり製造原価・削減試算 |
| 工場レイアウト | 図面JSONを取り込み工程と設備を対応づけ。滞留が帯として乗る。動線の長さ×滞留で「遠い＋待つ」区間を抽出。全画面ビューに縮尺とズーム |
| データ品質 | この数字がどこから出たかの開示。欠損を4段階（実績／近似／日付のみ／除外）で記録 |
| 列の対応づけ | CSVの列と意味の紐付け。自動推測するが必ず確認できる |
| 書き出し | **稟議用PNGを1枚。**流れの図版とレイアウト重ね版の2種類 |

**出口＝PNG**

コードにこう書いてある。

```
// 稟議に貼れる一枚（PNG書き出し）★このアプリの出口
// 「担当者が上司に説明でき、稟議に貼れる一枚」を吐き出すこと。
// 画像は口頭説明なしで渡るので、根拠が図の中に無いと決裁の場で必ず止まる。
```

**このアプリの成果物は画面ではなくPNG。**画面はそこに至る過程にすぎない。

## 3. 指示書が定めていた制約（＝設計思想の原資料）

元の指示書に明記されていたルール。**これが「どういうストーリーで作ったか」の一次資料**にあたる。

| 条項 | 内容 |
| --- | --- |
| §2-2 | データ仕様の未確認項目を推測で埋めない。止まって聞く |
| §3-1 | **CSVの中身を絶対にサーバーに送らない。**全処理をブラウザ内で。localStorageにも保存しない（設定のみ） |
| §10-1 | 外部データは必ず単一の正規化関数を通す |
| §10-3 | **予定と実績を絶対に混同しない** |
| §10-4 | **計算できない値を0にしない。**nullにして除外件数を報告する |
| §10-5 | 同じ指標を2箇所で計算しない |
| §10-6 | **断定表現を出力しない。**「削減できます」ではなく「御社の入力値に基づく試算です」 |
| §10-7 | 単位の違う数量を合計しない |
| §10-11 | **APIキーをクライアント側に置かない** |
| §12 | 「型が通った・テストが緑」は検証ではない。実ブラウザで確かめる |
| §14 | 日本語で、短い注釈をつけて説明する（初心者向け） |

### ここから読み取れる設計思想

**設計判断のほぼ全部が、ひとつの問いに答えている。**

> 「その数字、本当ですか？」と聞かれたときに耐えられるか

だから、普通なら見栄えが悪くなる方向に倒している。

- 除外した件数を画面に出す（隠すと指摘された瞬間に全部が疑わしくなる）
- 単価未設定を0円で混ぜない（混ぜると凍結額が**実際より小さく**出る）
- 健全な工場のデータでは騒がない（いつも「問題あり」と言う道具は信用されない）

**盛らないことが機能になっている。**

コード内の他のコメントも同じ方向を向いている。

```
QualityPanel : 目利きの決裁者に「これ何のデータ？」で止められないための唯一の防具
calendar.ts  : 暦時間だけで「63.5時間止まっています」と出すと、現場を知っている決裁者に見抜かれる
lotView.ts   : 平均だけ見せて終わりにすると、目利きの決裁者に「で、それは本当か」で止められる
```

**想定読者は一貫して「決裁者」。**説明者がその場にいない状況を前提に作られている。

## 4. 実データについて判明していること

### CSV仕様（製品ソースから確定済み。推測ではない）

根拠の行番号は `docs/phase0-data-findings.md` にある。

- **実績の開始列は `作業開始日時` で、「実績」の語を含まない。**同じCSVに `開始予定日時` が並び、**列の並びは予定のほうが先**。「開始を含む列」で探すと予定を掴む
- **単位の列が無い。**品目マスタ側にあるため、単位は手入力で持つ
- 日時の書式が2種類ある（`2026/08/17 14:30:00` と `2023/1/1 10:00`）
- 文字コードは顧客が選べる（UTF-8 / Shift_JIS の選択肢が実在）

### 実データ（検証環境API）を取った結果 ── 良くない

| | 値 |
| --- | --- |
| 実績時刻のあるロット | **10%** |
| 除外 | **90%** |
| 総リードタイム | 869日 |
| 工程数 | **69**（工程コードが品目ごとに振られていたため） |

アプリは正しく振る舞い、90%を除外して「105件から算出」と表示した（捏造しなかった）。
だが**この数字では商談に出せない。**

**ただし、これは検証環境のデータが壊れているせいの可能性が高い。**管理画面で確認したところ：

```
工程指示のリードタイム   353,440,005 秒（＝約11年）
工程ごとの良品数         7,500,000,000,000,000,000,000,000,000,000,000
```

桁が壊れている。**検証環境では「使えるか」の判断はできない。**

### まだ分かっていない致命的な2点

1. **実際の顧客は `作業開始日時` / `作業終了日時` を入力しているか？**
   日付のみの運用が多数派なら、このアプリは前提から成立しない
2. **工程コードは品目ごとに振られるのが普通か？**
   検証環境ではそうだった。それが標準なら工程が数十個になり図が破綻する（工程名で束ねる回避策は実装済み）

**どちらも社内の導入・CS担当に聞けば5分で分かる。**

## 5. 既存システムの調査結果 ← 今日の最重要事項

Smart Craft管理画面（検証環境）を実際に操作して棚卸しした。

### 既にある機能

| 機能 | 中身 |
| --- | --- |
| ダッシュボード | 稼働・遅延・納期超過の件数。レイアウト編集可、全体／担当者／設備の3タブ |
| ガントチャート | 製造指示の時間軸。**工程まで展開でき、実績も重ねられる。**スケジュール編集も可 |
| AIアシスタント | 「今月の生産実績を教えて」等に自然言語で回答。利用枠あり |
| 分析レポート | 生産性分析／設備稼働分析／不良分析。**利用者が自分でグラフを組むビルダー** |
| 実績エクスポート | CSV書き出し |
| 在庫数推移 | 在庫の時系列 |

### 生産性分析で選べる指標（実物を確認）

```
★製造指示のリードタイム        ← 既にある
★工程指示のリードタイム        ← 既にある
 サイクルタイム（担当者の実稼働時間 / 担当者の稼働時間 / 工程の稼働時間）
 工程の稼働時間（実稼働＋中断）
 担当者の稼働時間（実稼働＋中断）
 工程の稼働率
 標準時間（良品数で計算）
 標準時間 ÷ 工程の稼働時間 × 100
 標準時間 ÷ 工程の実稼働時間 × 100
 標準時間 ÷ 担当者の稼働時間 × 100
 担当者の稼働時間 ÷ 標準時間 × 100
 工程の稼働時間 ÷ 標準時間 × 100
 工程ごとの良品数 / 製造指示ごとの良品数 / 指示数量
```

**軸**：品目・品目グループ・工程・設備・担当者・日・シフト・製造指示
**絞り込み**：品目分類／グループ／タグ、品目／タグ、製造指示番号／タグ、設備／タグ、作業区／タグ／区分、工程／ステータス／タグ、担当者／タグ、期間

作りかけの保存グラフが「テスト」「aaa」「工場A」等の名前で多数あり、社内で実際に使われている。

### つまり

**「リードタイムの可視化」は差別化にならない。既にある。**
ここは隠さずに認めるべきで、協議で伏せたら一撃で崩れる。

### では何が無いのか

指標を全部並べて気づいたこと：**すべてが「resource（工程・設備・担当者）がどれだけ効率よく動いたか」を測っている。**

| 問い | 既存機能 | |
| --- | --- | --- |
| 工程の中の時間は？ | 生産性分析 | ある |
| 製造指示全体のリードタイムは？ | 生産性分析 | ある |
| この1件はどう流れた？ | ガントチャート | ある |
| 設備は止まっていないか？ | 設備稼働分析 | ある |
| **工程と工程の間は何日？** | — | **無い** |
| **どの工程間が最も悪いか？** | — | **無い** |
| **それは何円分か？** | — | **無い**（システム全体に金額指標がゼロ） |
| **工場のどこで起きているか？** | — | **無い** |

### なぜ穴が空くのか（構造的な理由）

MESのデータは**工程ごとに記録される**ため、自然な集計は全部「工程ごと」になる。
ところが**工程と工程の間の待ち時間は、どの工程にも属さない。**だからどの行にも乗らず、どのグラフにも出てこない。

ガントチャートを開けば1件については目で見えるが、**1件ずつ**であり、数千ロットを束ねて
「どの工程間が恒常的に最も損しているか」は出せない。

## 6. これまでに立てたストーリー案と、その弱点

### 案A：指示書に暗黙に書かれていたもの

> 担当者が上司に説明でき、稟議に貼れる一枚を出す

**弱点**：何の稟議か書かれていない。誰の意思決定が変わるのか不明。

### 案B：今回提案した強い筋

> **MESベンダーの構造的な弱点を、自社データで塞ぐ仕組み**
>
> MESを売った後に必ず言われる「導入したけど入力の手間が増えただけ。で、いくら得したの？」に、
> **顧客自身のデータで、追加入力ゼロで**答える。
> 出てくるのは「効果がありました」ではなく「いま御社の床に◯円が止まっています」という現在の事実。

**なぜSmart Craftでなければできないか**：工程間の滞留は工程ごとの実績時刻が無いと計算できず、それを持つのはMESだけ。ERPにも生産管理パッケージにも無い。Excelでは実質不可能。

**この案の弱点（重要）**

1. **問題を見せるだけで解決はしない。**「9.8日待っています」と言われても待ち時間は減らないし、現場は薄々知っている。**一度見せて終わりなら価値は初回で尽きる**
   - → 対策は**継続監視**。「先月より2日悪化。原因はこの工程間」なら毎月ログインする理由になる。**フェーズ10（未着手）がこれにあたり、実は残作業ではなく本体**
2. **金額が運転資金であってP/Lの利益ではない。**「その1,200万円、返ってくるの？」に耐える説明が要る
3. **既存のビルダーに指標を1つ足せば大半は実現する。**軸も絞り込みも既にある。ビルダーで出せないのは金額換算・レイアウト重ね・PNG書き出しの3点のみ
4. **会社はAIアシスタントに投資している。**分析の入口がそちらに寄るなら、独立画面を増やす判断が妥当か不明

### 提案した立て付け

「新しいアプリを作りました」ではなく：

> **分析の構造的な盲点と、その試作**
> 1. 既存の分析指標を全部並べたら、工程と工程の間を測るものが一つも無い
> 2. リードタイムの大半はそこにある
> 3. 稼働率だけを追うと、そこが悪化することがある（各工程を止めないためのまとめ作りが仕掛を増やす）
> 4. 試作を作って動かした
> 5. 相談したいこと：既存分析への指標追加か別立てか／金額換算は要るか／AIアシスタントと競合しないか

**「使ってください」ではなく「盲点を見つけたので扱いを決めてください」**にすると承認を取りに行く形にならず、否定されても資料の価値が残る。

## 9. 次のチャットで考えてほしいこと

1. **誰のための機能か**を決める（顧客の担当者 / 自社の営業 / 自社のCS）
2. その人の**どの意思決定が変わるのか**を1文で書く
3. **2回目に開く理由**があるか（無ければ資料であって製品ではない）
4. **成功をどう測るか**を決める
5. 既存の分析レポートへの**指標追加で足りるのか**、別立てが要るのかを判断する

**いま欠けているのは仕様書ではなく企画書。**
指示書は「何を作るか」を精密に定めていたが、「なぜ作るのか」には答えていない。
社内で問われるのはまさにそこ。
